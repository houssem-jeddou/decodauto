# CLAUDE.md : règles de travail pour decodauto.com

Site en français pour la France : « Votre voiture vous alerte, on vous dit quoi faire. »
Guide indépendant : voyant, code défaut, symptôme ou obligation → peut-on rouler, gravité, coût probable, marche à suivre.

## Ce qui fait foi (décision de Houssem du 23/10/2026)
- Les documents de pilotage (01 à 05, 07, 08) font foi dans le **projet Claude « Site Voiture $$ »**. Le dossier `docs/` en est une **copie**, mise à jour à chaque validation par une pull request. Lire `docs/04_journal_avancement.md` (étape en cours, décisions, ce qui est figé), puis `docs/01`, `docs/02`, `docs/03`, `docs/08_structure_contenus.md` et `docs/09_plan_du_site.md` avant toute tâche. Si `docs/` semble en retard ou en contradiction, le signaler : ne pas trancher seul. Ne pas modifier `docs/` sans demande explicite.
- En cas d'écart entre le code et `docs/`, c'est `docs/` qui a raison : corriger le code, ou signaler l'écart.
- **Structure des contenus** : la transposition de `docs/08` est validée (23/10/2026). Ce sont désormais **les schémas du dépôt** (`src/schemas/`, contrôles dans `src/lib/controle.ts`) qui font foi ; `docs/08` est archivé comme référence lisible. Une modification de structure passe par une demande de changement (format dans `docs/03`), puis met à jour les schémas et `docs/08`.
- **Plan du site** : validé le 23/10/2026 (étape 4). C'est `data/plan-du-site.json` qui fait foi (pages, adresses, mots-clés, pages mères, liens) ; `docs/09` en est la vue lisible. Les liens entre pages viennent uniquement du plan : une page ne déclare pas de liens, et un lien écrit dans le texte ne mène qu'à une page liée dans le plan. Ajouter une paire de liens au plan se propose dans la pull request du lot de pages concerné, avec une ligne de justification, et Houssem la valide avec le lot (décision du 23/10/2026). Retirer un lien, ou toute autre modification du plan, passe par une demande de changement.
- Ce qui est figé (périmètre, mots-clés, structure validée, plan du site) ne bouge pas sans demande de changement acceptée par Houssem.

## Méthode (docs/03)
1. **Une branche et une pull request par tâche.** Ne jamais pousser sur `main`. Ne pas fusionner et ne rien déployer sans demande explicite.
2. **Contrôles verts avant de présenter.** `npm run schemas`, `npm test`, `npm run build` (inclut `scripts/controle.ts`) et `npm run liens` doivent passer. On ne contourne pas, n'affaiblit pas et ne désactive pas un contrôle pour faire passer un travail.
3. **Une source de vérité par sujet, rien recopié à la main** : plan du site (`data/plan-du-site.json`), base voyants (`data/voyants.json`), registre des sources (`data/sources.json`). Les pages en dérivent : adresse, thème, requête principale, niveau de sécurité sont calculés, jamais saisis.
4. **Contrôles cumulatifs.** Toute règle vérifiable par une machine devient un test (`tests/`, pages de test dans `tests/fixtures`). Les autres vont dans la liste de recette. Ne travailler que sur l'étape en cours ; deux exceptions : une seule piste technique à la fois, sans dépendance à un contenu non validé, peut avancer en parallèle : l'étape 7 avec sa porte, ou un livrable technique d'une autre étape contrôlé à la porte de cette étape (docs/03, règle 12). Seconde exception : une page en ligne fausse ou un incident en production se corrige tout de suite, par une pull request dédiée revalidée par Houssem (docs/03, règle 13) ; revue indépendante avant la fusion si la correction peut attendre une heure, sinon dans les 24 heures après la publication.
5. Ne rien affirmer « validé » sans preuve. Dire ce qui a échoué ou reste à faire.

### Porte de sortie, tags, revue indépendante, idées reportées (docs/03, règles 2, 3, 8, 9)
- **Porte de sortie par étape.** Une étape n'est terminée que lorsque ses critères mesurables (colonne « Porte de sortie » du tableau des étapes de `docs/03`) sont vérifiés **avec preuve** (sortie de commande, résultat de CI, lien), qu'un **agent indépendant** a relu l'ensemble, et que **Houssem a validé**. On ne passe pas à l'étape suivante sans les trois. Une date ne justifie jamais d'alléger une porte.
- **Tag Git par version validée.** Chaque version validée par Houssem est marquée d'un tag Git (retour arrière toujours possible). Claude ne crée, ne déplace et ne supprime un tag que sur demande explicite de Houssem, après sa validation ; jamais sur une version non validée.
- **Revue indépendante avant toute présentation** de ce qui sera validé, figé ou publié : relecteur sans contexte de la rédaction, à qui l'on donne le code et pas la conclusion ; chaque constat est étayé par des preuves (fichier, ligne, commande) ; deux revues au maximum par livrable, selon la règle n° 1 des instructions du projet.
- **Idées reportées.** Toute demande hors de l'étape en cours ou hors du périmètre figé n'est pas réalisée (sauf correction urgente, docs/03 règle 13) : elle est notée dans la section « Idées reportées » de `docs/04_journal_avancement.md` (proposée à Houssem ; après sa validation, Claude met `docs/` à jour par pull request) ou traitée par une demande de changement (format dans `docs/03`).
- **Fin de session.** Si quelque chose a été validé ou décidé : journal (`docs/04`) mis à jour, prévision des étapes comprise. Après la validation explicite de Houssem, notée au journal, Claude met à jour les documents du projet Claude et ouvre la pull request de la copie `docs/` ; Houssem ne charge que les fichiers joints (CSV) et décide des fusions et des tags. Ne pas modifier `docs/` sans cette validation.

## Règles de contenu (docs/01)
- **Jamais de verdict de sécurité inventé.** Un verdict (rouler ou non, urgence, action) vient de la base voyants ou est saisi avec au moins une citation de première main qui fixe un niveau (notice d'utilisation du constructeur, Sécurité routière, Légifrance, textes du contrôle technique, arrêté préfectoral, RappelConso ; le règlement ONU n° 121 ne sert qu'au symbole et à la couleur). Le niveau retenu est celui de la citation la plus prudente, ni moins ni plus (R3-PLUS-PRUDENT, R3-NIVEAU-SANS-SOURCE). Une ligne de la base voyants s'appuie sur les notices d'au moins 3 marques de référence de 2 groupes (`MARQUES_REFERENCE` dans `src/schemas/listes.ts`) : chaque citation donne la page ou la section, l'extrait et le niveau tiré de la notice selon la grille (`src/schemas/grille.ts`), le verdict le plus prudent l'emporte et l'écart est signalé (docs/03, règle 10 ; contrôles R3 et R8). Pas de relecteur extérieur : Houssem valide les verdicts sur un paquet de validation et relit l'encadré de décision de chaque page avant publication (docs/03, règle 7). Un voyant déclaré dans `voyants` a sa ligne reprise de la base (`- voyant: id`), jamais écrite à la main ; une ligne saisie liée à un voyant (`voyant_lie`) n'est jamais moins grave que ce voyant dans la base. Une relecture par une IA n'est pas une vérification. Houssem valide les verdicts : l'empreinte de validation ne se recalcule pas pour faire passer un contrôle. En cas de doute : recommander l'avis d'un professionnel, dire ce qu'on ne sait pas.
- **Jamais de prix d'enseigne ni de prix de prestation**, pas de requête d'achat générique. Le coût probable est une échelle en ordres de grandeur avec base de calcul sourcée.
- Chaque page s'ouvre sur la décision et contient un élément unique (arbre de décision, tableau, outil, photo réelle).
- Une intention de recherche = une seule page. Pas de page par modèle sans donnée constructeur sourcée.
- Pictogrammes redessinés par nos soins, jamais copiés. Codes défaut constructeur précisés par marque.
- **Transparence** : auteur identifié (page « à propos ») ; chaque page dit en une ligne comment elle est produite (rédaction assistée par une IA, sources de première main, verdicts et encadré de décision vérifiés par Houssem) ; la méthode détaillée est une section de « à propos » (docs/03, règle 11).
- Électrique, hybride, valises OBD, démarches administratives : hors périmètre (`docs/02`).

## Technique
- Astro **7.4.2** (version exacte), sortie 100 % statique, `site` = https://decodauto.com, `trailingSlash: 'always'`, `build.format: 'directory'`, `lang="fr"`. Node 22.23.4 pour les contrôles (`.nvmrc`; `engines` : `>=22`, Astro exige au moins 22.23.4). Toutes les dépendances sont figées sans `^` ni `~` (`.npmrc`: `save-exact`).
- **Non-indexation à double clé** : le site n'est indexable que si la variable `SITE_INDEXABLE` vaut exactement `true` **et** si le drapeau versionné `config/indexation.json` vaut `{ "indexable": true }` (`false` par défaut). Sinon `public/_headers` envoie `X-Robots-Tag: noindex` et chaque page a `<meta name="robots" content="noindex">`. Basculer le drapeau est une décision de Houssem, jamais une initiative de Claude. `robots.txt` ne contient jamais de `Disallow`. Ne jamais publier une vraie page en noindex en production. Le script de contrôle affiche le mode actif et vérifie la cohérence dans les deux sens ; `npm run verifier:modes` teste les quatre combinaisons.
- Toute page HTML du site construit correspond à une adresse du plan du site, ou est l'accueil ou la 404 : sinon la construction échoue.
- Éléments repérés dans la page construite : `data-element-unique="arbre-de-decision|tableau|outil|photo"` (un tableau a au moins une ligne de données), `<ol data-tutoriel-etapes>` pour les étapes d'un tutoriel, `data-encadre-decision` pour l'encadré de décision (un seul, premier bloc après le H1, rien de masqué, avec la question, la tranche de coût et une ligne `data-encadre-ligne` par situation portant `data-verdict` et `data-urgence`, les libellés de la grille et l'action) et `data-emplacement-pub` pour un emplacement publicitaire (jamais avant l'encadré).
- Pictogrammes de la base voyants : `src/pictogrammes/<id>.svg`, SVG autonomes contrôlés (PICTO-*). L'empreinte de validation verrouille l'encadré de décision de chaque page et chaque ligne de la base (`src/lib/empreinte.ts`).
- Cloudflare : fichiers statiques uniquement (`wrangler.json`, aucun script Worker, `workers_dev` et `preview_urls` à `false`, `not_found_handling` = `404-page`, domaine personnalisé decodauto.com en `custom_domain`). **Le déploiement ne passe que par le workflow GitHub Actions** (pas de script npm de déploiement) : uniquement sur `main`, si tous les contrôles sont verts et si les secrets `CLOUDFLARE_API_TOKEN` et `CLOUDFLARE_ACCOUNT_ID` existent. Un déclenchement hebdomadaire lance les contrôles (alertes de revue dépassée) sans jamais déployer. Ne jamais écrire un secret dans le dépôt.
- Les pages de test (`tests/fixtures`) ne sont jamais dans `src/content`, ni dans le plan du site, ni dans `dist` : le contrôle échoue sinon.
- Une fois le site en ligne et indexable, chaque fusion sur `main` publie : la liste de recette de l'étape 9 (docs/03) est repassée avant chaque fusion d'un lot de pages. Avant AdSense, les emplacements publicitaires ne sont pas affichés en production (emplacements factices dans une construction de test pour mesurer la stabilité de page).
- Catalogue des règles et des codes d'erreur : `CONTROLES.md`.

## Commandes
`npm ci` · `npm run dev` · `npm run build` (construit + contrôle) · `npm test` · `npm run schemas` · `npm run liens` · `npm run lighthouse` (après `build`) · `npm run fixtures` (régénère les pages de test) · `npm run plan:vue` (met à jour les parties générées de `docs/09`) · `npm run grille:vue` (parties générées de `docs/08` : marques de référence et grille) · `npm run empreinte -- <page.md> | --voyant <id>` (empreinte à copier après la validation de Houssem).
