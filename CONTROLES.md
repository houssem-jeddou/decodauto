# Contrôles automatiques

Lancés à chaque pull request (`.github/workflows/ci.yml`) ; `npm run build` lance aussi `scripts/controle.ts`. Exécuteur (demande de changement n° 27, suspendue tant que le dépôt est public par la n° 29) : chaque job tourne sur `${{ github.event.repository.private == true && vars.CI_RUNNER || 'ubuntu-latest' }}` : dépôt public, toujours les serveurs de GitHub ; dépôt privé, la variable du dépôt `CI_RUNNER` = `self-hosted` enverrait les jobs à l'exécuteur prévu dans Ubuntu (WSL) sur le PC de Houssem (`travaux/etape-8/executeur-wsl.md`, jamais installé), sans elle les serveurs de GitHub. Sur l'exécuteur, pas de cache npm de GitHub (`~/.npm` reste sur le PC) ; les rapports complets de Lighthouse ne sont conservés qu'en cas d'échec (les scores de chaque page restent dans le journal du job) ; délai du job Lighthouse : 30 minutes. Tests : `tests/site.test.ts` (groupe « CI : exécuteur, cache et stockage »).
Une erreur **bloque** (code de sortie 1, pas de déploiement). Une **alerte** s'affiche sans bloquer. Une **information** (`INFO`) est un simple constat, sans gravité.
Le script affiche en tête le **mode d'indexation actif**. Chaque lundi, le workflow relance les contrôles sur `main` (sans déployer) avec `--echouer-sur R5-REVUE-DEPASSEE,COUT-A-REVERIFIER,COUT-FOURCHETTE-A-REVOIR` : une revue dépassée, un montant à revérifier ou une fourchette à revoir font alors échouer ce run planifié, ce qui déclenche la notification GitHub. Ces alertes datées ne font jamais échouer une pull request.

## Production en ligne (`npm run production`, job « production » de la CI)
Sur `main` (après chaque déploiement réussi, chaque lundi, à la demande depuis l'onglet Actions) : un écart fait échouer le run. Juste après un déploiement (push sur `main`, option `--apres-deploiement`), Cloudflare peut servir l'ancienne version pendant environ une minute (point ouvert du 12/11/2026) : jusqu'à 4 passages à 30 secondes d'écart, sans nouveau passage au-delà de 4 minutes (`verifierAvecTentatives`) ; l'écart fait échouer s'il persiste au dernier passage, et les écarts des passages précédents restent affichés en avertissement et dans le résumé. Contrôle du lundi et lancement à la demande : un seul passage. Depuis la demande de changement n° 26 (minutes du dépôt privé), le job ne tourne plus sur une pull request ni sur une autre branche que `main` : il y était seulement informatif (`--information` : avertissements, job vert), la production n'ayant pas encore les changements de la branche et dépendant aussi des réglages Cloudflare, hors du dépôt ; l'option reste pour un lancement local. Le type fluide (vague C) n'a pas encore de modèle.
Références du texte rédigé, remplacées au rendu depuis les sources de vérité (`src/lib/modeles.ts`) :
- `{{notice:<source>}}` : marque, modèle, génération et édition de la notice (champ `modele` du registre, charte §2.5) ;
- `{{verdict:<voyant>}}` : libellé du verdict de la grille pour une ligne de l'encadré de la page (charte §2.1, jamais reformulé) ; `{{verdict:ligne-<n>}}` : celui de la n-ième ligne de l'encadré, saisie ou reprise de la base (livrable 6.6c). Il suit le numéro de la ligne : si l'ordre de l'encadré change, l'empreinte de l'encadré change aussi (revalidation par Houssem), et la recette relit chaque phrase qui cite un verdict ;
- `{{cite:<source>|<page ou section>}}` : page citée dans le texte seulement, ajoutée à la section « Sources » (charte §4, point 8) ;
- `{{montant:<id>}}` : texte d'un montant de `data/couts.json` déclaré dans le coût probable de la page (charte §2.3, livrable 6.6c) ;
- `{{tableau}}`, seul dans son paragraphe, juste avant un tableau Markdown : ce tableau devient l'élément unique de la page (`data-element-unique="tableau"`, bloc `.tableau-corps`, région nommée atteignable au clavier, qui défile seule si le tableau est trop large). Permis seulement sur un type dont le modèle ne construit pas l'élément unique (pneus et obligations, panne, dossier), si la page déclare `element_unique: tableau`, une seule fois, et suivi d'un tableau (livrable 6.6c) ;
- `{{arbre}}`, seul dans son paragraphe, juste avant une liste numérotée : chaque élément est une question, suivie de la liste à puces de ses réponses (au moins `REPONSES_MIN_ARBRE`, deux, chacune disant quoi faire ou à quelle question passer). La liste devient l'arbre de décision, élément unique de la page (`data-element-unique="arbre-de-decision"`, bloc `.arbre`, région nommée par le titre qui précède). Permis seulement sur une page panne qui déclare `element_unique: arbre-de-decision`, et alors obligatoire ; une seule fois (étape 10) ;

## Empreinte de validation
Code : `src/lib/empreinte.ts` ; calcul : `npm run empreinte -- <page.md>`, `npm run empreinte -- --voyant <id>`, `npm run empreinte -- --montant <id>` (montant ou prise en charge de `data/couts.json`) ou `npm run empreinte -- --charte` (textes affichés de la charte). L'empreinte se copie après la validation de Houssem, jamais pour faire passer un contrôle.
- **Ligne de la base voyants** (`validation` de `data/voyants.json`) : identifiant, nom, couleur, pictogramme et son dessin (contenu du fichier SVG ; espaces et commentaires ignorés), situation, verdict, urgence, action, écart entre marques et citations (source, page ou section, extrait, niveau). L'ordre des citations n'a pas d'effet.
- **Page éditoriale** (`validation` du frontmatter) : l'encadré de décision, c'est-à-dire la question de décision, les lignes de situation dans l'ordre (une ligne reprise de la base y figure par l'identifiant du voyant et ce que l'encadré en affiche : situation, verdict, urgence, action, écart ; les changer oblige à relire l'encadré, corriger une citation non ; une ligne saisie en entier, voyant lié compris) et le coût probable (v5 : plage calculée, par les identifiants de ses tranches ; pièces de chaque cause, dans l'ordre des causes, ou pièces de la page ; risque si l'on continue et ses citations ; montants et prises en charge par leur identifiant ; base de calcul ; sources). Reclasser une pièce dans `data/couts.json` change la plage, donc l'empreinte des encadrés qui l'affichent. Exigée sur toute page éditoriale, même sans ligne saisie.
- **Montant ou prise en charge** (`validation` dans `data/couts.json`) : identifiant, texte, date d'entrée en vigueur, sources et affichage automatique. La date de vérification n'y entre pas : la mettre à jour ne demande pas de revalidation. Mettre à jour un texte (nouveau tarif) fait valider l'entrée une fois, sans revalider les encadrés qui l'affichent.
- **Textes affichés de la charte** (`validation` de `data/charte-validation.json`) : mention en tête, signature (sans ses dates), ligne de transparence, titre, ancre et texte de la section « Méthode », calculés sur un registre fixe de trois notices : ajouter une notice au registre change la liste affichée sans demander de revalidation.
- Casse, accents, ligatures, ponctuation et espaces n'ont pas d'effet : une coquille de ce type ne demande pas de revalidation (« 5 % » = « 5% », « 1 000 » = « 1000 », « 2,5 » = « 2.5 »). Un mot, une lettre, un chiffre ou un signe qui porte un sens (−, +, <, >, ≤, ≥, ±, €, %, °) changé demande une revalidation. Le reste du texte de la page se corrige librement.
